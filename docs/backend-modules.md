# Modules métier — SmartTaxi

## 1. Objectif du document

Ce document décrit les onze modules métier du backend SmartTaxi, chacun destiné à être organisé comme une unité cohérente au sein du monolithe modulaire, avec des frontières claires vis-à-vis des autres modules (voir [docs/backend-architecture.md](backend-architecture.md)).

**Cette liste est la liste canonique**, issue du SmartTaxi Master Prompt (Partie 3). Elle remplace une précédente version de ce document dont les noms de modules (Customers, Drivers, Rides, Vehicles, Payments, Rewards) ne correspondent plus à la spécification métier actuelle.

Pour le détail complet de chaque module (entités, statuts, événements, règles métier précises), voir [docs/business-functional-specification.md](business-functional-specification.md), qui fait foi en cas de divergence avec ce document. Ce document-ci reste la carte concise des modules et de leurs interactions.

Les modules **Identity**, **Fleet** et **Ride** sont implémentés à ce jour, les modules **Payment**, **Subscription**, **Notifications** et **Loyalty** le sont partiellement (voir [docs/backend-audit-report.md](backend-audit-report.md) pour l'état d'Identity ; le rapport final de la Phase 3 couvre l'implémentation de Fleet ; le rapport final de la Phase 4 couvre l'implémentation de Ride ; le rapport final de la Phase 5 couvre le sous-ensemble de Payment implémenté ; le rapport de Module 5 couvre le sous-ensemble de Subscription implémenté ; le rapport de Module 6 couvre le sous-ensemble de Notifications implémenté ; le rapport de Module 7 couvre le sous-ensemble de Loyalty implémenté ; voir la section 11 ci-dessous pour le sous-ensemble Support/Incidents implémenté du Module 11 ; voir la section 12 ci-dessous pour le sous-ensemble Analytics & Reporting (Module 12), le sous-ensemble Administration — comptes admin, verrouillage de connexion, journal d'audit (Module 13A) — et le durcissement applicatif transverse (Module 13B — rate limiting, health checks, CORS, HSTS, middleware de corrélation) implémentés) : le reste du périmètre de Payment/Subscription et le reste d'Administration (`SystemSetting`, feature flags, géographie, rôles administratifs supplémentaires) restent à l'état de spécification ; le déploiement/l'exploitation (Docker, CI/CD, Kubernetes, observabilité externe type Prometheus/Grafana/OpenTelemetry) n'a jamais été dans le périmètre applicatif de ce backend et reste entièrement non démarré — voir section 12 pour le détail exact de cette frontière.

## 2. Identity

- **Objectif** : gérer l'identité et l'accès des utilisateurs de la plateforme, tous rôles confondus.
- **Responsabilités** : authentification, gestion des comptes, rôles multiples et permissions fines, émission/validation/rotation/révocation des tokens, vérification email/téléphone, 2FA, gestion de session, documents utilisateur, codes de parrainage.
- **Rôles supportés** : Customer, Driver, TaxiOwner, GaragePartner, RoadsideAssistancePartner, Advertiser, AdvertiserAdmin, PlatformAdmin, SuperAdmin, SupportAgent, FinanceManager, FleetManager, OperationsManager, ContentModerator, SecurityOfficer — un même compte peut cumuler plusieurs rôles.
- **Données sensibles** : identifiants de connexion, mots de passe (hachés), tokens, documents d'identité, données personnelles.
- **Interactions** : module transverse, utilisé par tous les autres modules pour authentifier et autoriser les actions.
- **Règles d'isolation** : aucun autre module ne stocke de logique d'authentification propre ; toute vérification d'identité passe par Identity.

## 3. Subscription

- **Objectif** : gérer les abonnements des acteurs éligibles (Customer, Driver, TaxiOwner, GaragePartner, RoadsideAssistancePartner, Advertiser, BusinessCustomer).
- **Responsabilités** : plans configurables (prix, période de facturation, essai, fonctionnalités, limites), activation, renouvellement, suspension, annulation, expiration, upgrade/downgrade, périodes de grâce, entitlements.
- **Données sensibles** : historique de facturation.
- **Interactions** : Identity (rôle cible du plan), Payment (facturation), Fleet/Advertising/Maintenance/RoadsideAssistance (fonctionnalités conditionnées par abonnement).
- **Règles d'isolation** : les vérifications d'accès à une fonctionnalité passent par un service d'entitlement dédié, jamais dispersées dans les contrôleurs.
- **État d'implémentation** : un sous-ensemble ciblé est implémenté — plans configurables (CRUD admin, activation/désactivation), abonnement (souscription, renouvellement, annulation, upgrade/downgrade), cycle de vie `Pending → Active → Suspended/Cancelled/Expired` avec garde d'unicité en base (un seul abonnement Pending/Active par abonné et par rôle), service d'entitlement (`ISubscriptionEntitlementService`), facturation via une extension additive et minimale du module Payment (`SubscriptionCharge`, passerelle simulée déterministe — aucune passerelle réelle n'existe encore dans Payment lui-même). Depuis Module 6, l'activation, le renouvellement, l'annulation et l'expiration d'un abonnement notifient chacun l'abonné via `INotificationDispatcher` (catégorie Subscription, non obligatoire). **Hors périmètre de cette phase** (non implémenté) : périodes de grâce, offres promotionnelles, proratisation lors d'un upgrade/downgrade, purge planifiée des abonnements expirés (seul un balayage manuel `expire-due` existe, dans l'esprit du balayage manuel déjà utilisé par Fleet) ; Ride/Fleet ne consomment pas encore le service d'entitlement (Loyalty, Module 7, en est le premier consommateur réel — via `GetEntitlementAsync`, jamais par lecture directe des tables Subscription). Détails complets dans le rapport de Module 5.

## 4. Ride

- **Objectif** : gérer le cycle de vie complet d'une course (immédiate, planifiée, négociée, partagée).
- **Responsabilités** : recommandation de chauffeurs (score explicable), sélection manuelle obligatoire par le client, réponse du chauffeur, transitions de statut contrôlées, chat temporaire, suivi de localisation, annulation, complétion, SOS, notation.
- **Règle absolue** : le client choisit toujours manuellement son chauffeur ; le backend ne doit jamais assigner automatiquement un chauffeur.
- **Données sensibles** : géolocalisation, itinéraire, horodatage, contenu du chat.
- **Interactions** : Identity (client/chauffeur), Fleet (véhicule), Payment (règlement), Loyalty (gains de points), Notifications (alertes), Administration (SOS/litiges).
- **Règles d'isolation** : Ride orchestre le processus métier sans dupliquer les données détenues par Identity ou Fleet.
- **État d'implémentation** : implémenté (Domain/Application/Infrastructure/API + hub SignalR + migrations + tests unitaires et d'intégration Postgres). Détails complets, écarts assumés par rapport à la spécification et limitations connues dans le rapport final de la Phase 4 et dans `docs/business-functional-specification.md` (Module 3). Payment/Loyalty/Notifications n'existant pas encore, Ride prépare uniquement les points d'intégration (`AwaitingPayment`, événements documentés) sans écriture financière réelle.

## 5. Fleet

- **Objectif** : gérer le référentiel des propriétaires, flottes, véhicules et chauffeurs, ainsi que leurs affectations et contrats.
- **Responsabilités** : fiche véhicule, documents véhicule, affectations chauffeur-véhicule (avec historique et détection de conflits), contrats propriétaire-chauffeur, partage de revenus configurable, dépenses de flotte.
- **Données sensibles** : immatriculation, documents administratifs, identité du propriétaire.
- **Interactions** : Identity (chauffeur/propriétaire), Ride (véhicule utilisé), Maintenance (suivi technique), Payment (partage de revenus, dépenses).
- **Règles d'isolation** : Fleet est la source de vérité unique pour les données d'un véhicule ; les autres modules la référencent par identifiant. Un document véhicule expiré peut suspendre automatiquement le véhicule.
- **État d'implémentation** : implémenté (Domain/Application/Infrastructure/API + migrations + tests unitaires et d'intégration Postgres). Détails complets, limitations connues et décisions de sécurité dans le rapport final de la Phase 3. Le rattachement automatique d'un document véhicule expiré à la suspension du véhicule (ligne ci-dessus) n'est pas encore câblé en tâche planifiée — seul le balayage manuel (`expire-sweep`) existe à ce jour.

## 6. Maintenance (Module 9 — implémenté)

- **Objectif** : gérer le suivi technique et l'entretien des véhicules via des garages partenaires. La spécification métier nomme cette section « Module 5 » (`docs/business-functional-specification.md`) ; la séquence d'implémentation réelle l'appelle « Module 9 » — la spécification reste la source de vérité fonctionnelle, la numérotation d'implémentation est purement pratique.
- **État d'implémentation** : implémenté — `GarageProfile` (profil métier fin, 1:1 avec `UserId`, réutilise entièrement l'approbation de compte professionnel et le rôle `GaragePartner` déjà existants dans Identity, sans dupliquer d'état), cycle de vie complet de `MaintenanceRequest` (`PendingGarageResponse → QuotePending → QuoteSubmitted → QuoteAccepted → VehicleReceived → InProgress → WaitingForParts → Completed`, plus `Rejected`/`QuoteRejected`/`Cancelled`/`Disputed`) avec transitions atomiques au niveau repository, carnet d'entretien numérique immuable (`MaintenanceRecord`, lignes de prestations/pièces en value objects, créé une seule fois — aucune méthode de correction), intégration Fleet via `VehicleOperationalStatus.UnderMaintenance` avec des transactions atomiques dédiées pour le démarrage, la complétion et l'annulation forcée d'une intervention (`IMaintenanceWorkStartRepository`/`IMaintenanceCompletionRepository`/`IMaintenanceForceCancelRepository` — une seule transaction de base de données, jamais deux opérations indépendamment validées, jamais de réactivation forcée d'un véhicule suspendu pour une autre raison), intégration `FleetExpense` (dépense authentique créée à la complétion, catégorie Maintenance, jamais un second système de dépenses), règlement via le grand livre Finance existant (`MaintenanceBillingService`, `LedgerEntryType.MaintenanceRevenue` additif, convergence idempotente identique au pattern Advertising), intégration Notifications (`NotificationCategory.Maintenance`, ajout additif), recommandations d'entretien préventif basées sur des règles de date (moteur à règles, pas de ML, aucun ordonnanceur — balayage manuel).
- **Hors périmètre à ce jour** (délibérément différé) : pas de gestion complète d'inventaire de pièces détachées, pas de moteur de maintenance prédictive avancé, workflow `WaitingForParts`/`Disputed` limité aux statuts eux-mêmes (pas de logique de résolution étendue), aucune commission plateforme sur le règlement.
- **Responsabilités** : recommandation de garage (score explicable, sélection manuelle obligatoire), rendez-vous, devis, interventions, carnet d'entretien numérique (immuable sauf correction auditée), recommandations d'entretien (moteur à règles, pas de ML).
- **Données sensibles** : historique technique du véhicule, coûts d'intervention.
- **Interactions** : Fleet (véhicule concerné, lecture/écriture additive), RoadsideAssistance (suite d'une intervention d'urgence — Module 10 y crée une `MaintenanceRequest` via le seam public `TryAddAsync`, jamais d'écriture directe dans les autres tables Maintenance), Payment (grand livre, écriture additive).
- **Règles d'isolation** : Maintenance ne modifie jamais directement les données d'identité du véhicule détenues par Fleet.

## 7. Roadside Assistance (Module 10 — implémenté)

- **Objectif** : gérer les interventions d'urgence en cas de panne ou d'incident sur la route. La spécification métier nomme cette section « Module 6 » (`docs/business-functional-specification.md`) ; la séquence d'implémentation réelle l'appelle « Module 10 » — la spécification reste la source de vérité fonctionnelle, la numérotation d'implémentation est purement pratique.
- **État d'implémentation** : implémenté — `RoadsidePartnerProfile` (profil métier fin, 1:1 avec `UserId`, réutilise entièrement l'approbation de compte professionnel et le rôle `RoadsideAssistancePartner` déjà existants dans Identity), cycle de vie complet de `RoadsideAssistanceRequest` (`PartnersAvailable → PendingPartnerResponse → Accepted → PartnerOnTheWay → PartnerArrived → InProgress → Completed`, plus `Cancelled`/`Expired`/`Disputed` et `Rejected` — délibérément non terminal, retour explicite du demandeur à `PartnersAvailable` pour sélectionner un autre partenaire), recommandation de partenaire déterministe (compatibilité type de service/catégorie de véhicule/ville, distance Haversine uniquement quand les deux coordonnées existent réellement, jamais de note ni d'ETA inventées) avec **sélection manuelle exclusive, aucune diffusion façon marketplace** — un partenaire non sélectionné n'a jamais accès à la demande, historique de sélection append-only (`RoadsidePartnerSelectionHistory`, un cycle par sélection, une ligne résolue n'est jamais réécrite), types de service `Towing`/`MechanicalBreakdownAssistance`/`AccidentAssistance`/`BatteryJumpStart`/`TireReplacement`/`FuelDelivery`/`Unlocking`, intégration Fleet via `VehicleOperationalStatus.UnderRoadsideAssistance` — activée uniquement pour les trois types de service immobilisants (`Towing`/`MechanicalBreakdownAssistance`/`AccidentAssistance`) via des transactions atomiques dédiées au même pattern que Maintenance (`IRoadsideWorkStartRepository`/`IRoadsideCompletionRepository`/`IRoadsideForceCancelRepository`), les quatre autres types de service ne touchent jamais Fleet, lien `RideId` optionnel validé en lecture seule auprès de Rides (jamais de mutation de la course, aucun nouveau statut de course), transfert explicite et manuel vers Maintenance (`EscalateRoadsideRequestToMaintenanceCommand`, réutilise tel quel le seam public `MaintenanceRequest.Create`/`IMaintenanceRequestRepository.TryAddAsync`, idempotent — une seule `MaintenanceRequest` même en cas de nouvelle tentative —, jamais d'écriture directe dans les autres tables Maintenance ni de sélection automatique de garage), règlement via le grand livre Finance existant (`RoadsideAssistanceBillingService`, `LedgerEntryType.RoadsideAssistanceRevenue` additif, même convergence idempotente que Maintenance/Advertising), intégration Notifications (`NotificationCategory.Roadside`, ajout additif).
- **Hors périmètre à ce jour** (délibérément différé) : aucun moteur de répartition/dispatch réel, aucun fournisseur d'ETA ou de routage, aucune note ni état de disponibilité/occupation des partenaires, aucun workflow complet de résolution de litige (`Disputed` reste un simple indicateur gelant le règlement, sans processus de résolution), aucun catalogue de types de service configurable par l'administration, aucune création automatique d'Incident (le module Support/Incidents, Module 11, expose désormais `CreateIncidentFromRoadsideCommand`, mais uniquement comme déclenchement manuel admin — aucun hook automatique n'a été ajouté dans RoadsideAssistance).
- **Responsabilités** : réception des demandes, recommandation de partenaire (score explicable, sélection manuelle obligatoire), suivi de l'intervention, création d'incident pour les événements graves.
- **Règle absolue** : jamais d'assignation automatique d'un partenaire d'assistance.
- **Données sensibles** : géolocalisation en temps réel, données de sécurité liées à l'incident.
- **Interactions** : Ride (lien optionnel, lecture seule), Fleet (véhicule concerné, lecture/écriture additive pour les types de service immobilisants uniquement), Maintenance (transfert explicite et manuel via le seam public), Payment (grand livre, écriture additive).
- **Règles d'isolation** : RoadsideAssistance ne gère pas la facturation elle-même ; elle transmet les événements pertinents à Payment.

## 8. Loyalty (Module 7 — implémenté)

- **Objectif** : gérer la fidélité et récompenser les parrainages — Identity reste propriétaire de la relation de parrainage elle-même (Module 1).
- **État d'implémentation** : implémenté — deux types de points distincts jamais fusionnés (`RewardPoints` dépensables et expirables, `StatusPoints` déterminant uniquement le palier `Bronze`/`Silver`/`Gold`/`Platinum`, jamais dépensés), grand livre de points immuable (`LoyaltyPointLedgerEntry`, aucune ligne jamais modifiée ou supprimée — les corrections passent par une écriture `AdminAdjustment` compensatoire), catalogue de règles de gain configurables (`LoyaltyEarningRule`, décimal, jamais de virgule flottante, points arrondis à l'entier inférieur), seuils de palier configurables (`LoyaltyTierThreshold`, catalogue à 4 lignes seedé par migration), catalogue de récompenses (`LoyaltyReward`), rachat (`LoyaltyRedemption`), récompense de parrainage (`LoyaltyReferralReward`, une ligne par `ReferralId` — jamais deux fois), défis (`LoyaltyChallenge`/`LoyaltyChallengeProgress`, critères limités à ce que Loyalty peut évaluer depuis ses propres données : nombre de trajets payés, nombre de parrainages récompensés).
- **Déclencheur de gain — règle d'architecture non négociable** : uniquement la confirmation de paiement (`ConfirmPaymentCommandHandler`, via `ILoyaltyEarningDispatcher`), jamais la fin de course seule. Preuve : `CompleteRideCommandHandler` amène la course à `AwaitingPayment`, pas à `Completed` — seule la confirmation de paiement l'amène à `Completed`. Le client (payeur) et le chauffeur sont tous deux des acteurs éligibles pour un même trajet payé.
- **Intégration Subscription** : le multiplicateur de points passe exclusivement par `ISubscriptionEntitlementService.GetEntitlementAsync` (clé `Limits["LoyaltyPointsMultiplierPercent"]`, retombant sur 100 % si absente) — Loyalty ne lit jamais directement les tables Subscription/SubscriptionPlan.
- **Intégration Identity (parrainage)** : Identity détermine la relation de parrainage et son statut `RewardEligible` (`Referral`, `ReferralStatus`, `EvaluateReferralActivationCommandHandler` — réutilisés tels quels, un seul ajout minimal : `IReferralRepository.GetRewardEligibleAsync`). Loyalty décide seul du montant et de l'octroi de la récompense.
- **Explicitement hors périmètre** : badges, portefeuille cashback, solde de crédit promotionnel, transfert de points (non prévu par la spécification actuelle). L'application réelle d'une remise sur trajet/abonnement (`RideDiscount`/`SubscriptionDiscount`) reste non exécutable — Payments n'expose aujourd'hui aucun mécanisme de remise/coupon ; ces types de récompense sont modélisés au catalogue mais leur rachat est explicitement rejeté.
- **Données sensibles** : historique de consommation associé à un profil utilisateur.
- **Interactions** : Identity (parrainage, lecture seule), Subscriptions (multiplicateur, lecture seule via l'entitlement service), Payments (déclencheur de gain, lecture seule), Notifications (`NotificationCategory.Loyalty`, envoi via `INotificationDispatcher`) — jamais de lecture/écriture directe des tables de ces modules.
- **Règles d'isolation** : toute opération de points passe par le grand livre immuable ; jamais d'écrasement direct d'un solde — le solde mis en cache sur `LoyaltyAccount` n'est modifié que par une mise à jour conditionnelle atomique, dans la même transaction que l'écriture du grand livre.

## 9. Payment (Finance, Invoicing, Cash Register)

- **Objectif** : fournir la fondation financière complète de la plateforme.
- **Responsabilités** : paiements (passerelle mock configurable), commissions configurables, partage de revenus chauffeur-propriétaire, comptes financiers internes, grand livre comptable immuable, remboursements, versements (payouts), factures, taxes, encaissements espèces, sessions de caisse, déclarations de caisse chauffeur, clients professionnels, litiges financiers, rapports.
- **Devise par défaut** : TND.
- **Données sensibles** : données de paiement, informations bancaires, historique des transactions.
- **Interactions** : quasiment tous les modules (Ride, Fleet, Maintenance, RoadsideAssistance, Subscription, Loyalty, Advertising) déclenchent des écritures financières.
- **Règles d'isolation** : Payment est le seul module autorisé à manipuler des données financières ; toute correction utilise une écriture d'extourne, jamais une suppression.
- **État d'implémentation** : un sous-ensemble ciblé est implémenté (Phase 5) — paiement de course (Cash/Card/CashAtAgency), statuts, facture et reçu générés à la confirmation, partage de revenus chauffeur-propriétaire basé sur les contrats Fleet, commission plateforme configurable, remboursements (total/partiel/annulation) audités, historique de transaction immuable, rapports de revenus, grand livre comptable, versements (payouts), sessions de caisse, déclarations de caisse chauffeur, clients professionnels, litiges financiers, taxes, facturation groupée. **Extension Module 5** : un sous-ensemble additif et minimal (`SubscriptionCharge`, `ISubscriptionChargeCollector`) permet au module Subscription de facturer un abonné sans dupliquer `Payment`/`Invoice` (qui restent liés à une course) ni construire un second système de paiement — passerelle simulée déterministe, comme le reste de Payment. **Hors périmètre à ce jour** (non implémenté) : passerelle de paiement réelle pour Payment comme pour Subscription. Détails complets dans le rapport final de la Phase 5, le rapport de Module 5, et dans `docs/business-functional-specification.md` (Module 9).

## 10. Advertising (Module 8 — implémenté, cœur digital uniquement)

- **Objectif** : gérer les campagnes publicitaires diffusées sur la plateforme. La spécification métier nomme cette section "Module 9" (`docs/business-functional-specification.md`) ; la séquence d'implémentation réelle l'appelle "Module 8" — la spécification reste la source de vérité fonctionnelle, la numérotation d'implémentation est purement pratique.
- **État d'implémentation** : le **cœur digital** est implémenté — `AdvertiserProfile` (métadonnées business/facturation, 1:1 avec `UserId`, réutilise entièrement l'approbation de compte professionnel et le rôle `Advertiser` déjà existants dans Identity, sans dupliquer d'état), cycle de vie complet de `AdCampaign` (`Draft/Submitted/UnderReview/ChangesRequested/Approved/Scheduled/Active/Paused/Suspended/Completed/Cancelled/Rejected`) avec transitions atomiques au niveau repository, protection anti-auto-révision, invalidation automatique de l'approbation lors d'une modification substantielle (ciblage/dates/budget/tarification/emplacement — resoumission automatique en `Submitted`), historique de revue immuable (`AdvertisingCampaignReviewHistory`), catalogue d'emplacements administrable (`AdvertisingPlacement`), médias/créatifs versionnés (`CampaignCreative`, jamais modifiés en place) avec scanner de sécurité **mock** (`IFileSecurityScanner`/`DevFileSecurityScanner` — nouvelle abstraction, aucun fournisseur externe réel), budget opérationnel (`BudgetLimit`/`ConsumedBudget`/`DailyBudgetLimit` — jamais un compte financier, consommation atomique garantie sous concurrence, garde défensive `EndAtUtc > utcNow` en plus du `Status`), modèles de tarification `Flat/Duration/Cpm/Cpc`, impressions/clics en append-only avec clé d'idempotence dérivée d'un jeton de diffusion signé et à courte durée de vie (`IAdDeliveryTokenService`, Data Protection API — émis par `RequestAdDeliveryCommand`, lié à la campagne/l'emplacement/l'utilisateur authentifié ; corrige une faille d'audit où une clé d'idempotence arbitraire fournie par le client permettait de fabriquer des impressions/clics et d'épuiser le budget de n'importe quelle campagne), aucune donnée passager, API self-service annonceur et API admin de revue/configuration, intégration Notifications (`NotificationCategory.Advertising`, ajout additif), et une intégration Finance réelle avec convergence idempotente en cas d'échec partiel entre l'écriture du grand livre et le marquage `SettledAtUtc` (voir ci-dessous — le grand livre s'est avéré opérationnel à la vérification, contrairement à une évaluation initiale erronée).
- **Hors périmètre à ce jour** (délibérément différé, documenté explicitement) : gestion d'agences (un annonceur gère plusieurs comptes), publicité physique sur véhicules (écrans embarqués, extérieur/intérieur), consentement propriétaire/chauffeur, installation et inspection physiques, partage de revenus vers TaxiOwner/Driver pour la publicité physique, catalogue de zones géographiques contrôlé (le ciblage par ville utilise une chaîne libre normalisée, documentée comme limitation temporaire), moteur de diffusion interne réel pour écrans, fournisseur de modération de contenu réel, intégration automatisée avec les récompenses Loyalty (`LoyaltyRewardType.PartnerOffer` existe mais n'est pas câblé), fournisseur de facturation externe réel.
- **Intégration Finance** : réutilise directement les abstractions Payment existantes (`IFinancialAccountRepository.GetOrCreateAsync(FinancialAccountType.Advertiser, ...)`, `IFinancialLedgerRepository.PostBatchAsync`) via un nouveau service Application (`AdvertisingBillingService`, même convention que `LedgerPostingService`) — aucun second grand livre, aucun wallet. Un nouveau type d'écriture additif `LedgerEntryType.AdvertisingRevenue` a été ajouté. Le règlement reste un déclenchement explicite (`SettleCampaignBudgetCommand`), une facturation automatique/récurrente restant hors périmètre.
- **Responsabilités prévues mais différées** : gestion des annonceurs et agences (multi-comptes), consentement propriétaire/chauffeur, sélection de véhicules physiques, contrats et devis négociés, installation et inspection, moteur de diffusion interne pour écrans embarqués, partage de revenus physique, détection de fraude avancée.
- **Données sensibles** : données contractuelles et de facturation des annonceurs ; jamais d'exposition de l'identité individuelle des passagers — ciblage et performance restent agrégés (aucune donnée utilisateur individuelle dans les résultats).
- **Interactions réellement câblées** : Identity (rôle Advertiser, approbation de compte professionnel — lecture seule), Payment (`IFinancialAccountRepository`/`IFinancialLedgerRepository` — lecture/écriture additive), Notifications (`INotificationDispatcher` — lecture seule). **Aucune modification de Fleet, Rides, ou Subscriptions** dans cette phase digitale.
- **Règles d'isolation** : le ciblage et les analytics restent agrégés et privacy-aware ; aucune sélection d'utilisateurs nommés n'est possible.

## 11. Notifications (Module 6 — implémenté) / Communication, Support et Incidents (Module 11 — Support/Incidents implémentés, Administration non implémentée)

### 12A. Administration — comptes admin, verrouillage de connexion, journal d'audit (Module 13A pratique — partiellement implémenté)

**DELIVERED — Module 13A**

- **Gestion administrative de compte** (`SmartTaxi.Domain/Application/Infrastructure/API.Administration`) — quatre actions, chacune administrant **un autre compte** que celui de l'administrateur (jamais un mécanisme self-service alternatif) :
  - **Suspension** (`POST /api/admin/users/{userId}/suspend`) : bascule atomique `User.IsActive → false` (garde conditionnelle `ExecuteUpdateAsync`, jamais lecture-puis-écriture) **et** révocation de toutes les sessions actives de la cible (`ISessionRepository.RevokeAllActiveSessionsAsync`, nouvelle raison `SessionRevocationReason.AdminAction`) **et** écriture de l'entrée d'audit `AdminUserSuspended` — les trois dans une seule transaction base de données ; échoue en conflit si la cible est déjà suspendue.
  - **Réactivation** (`POST /api/admin/users/{userId}/reactivate`) : bascule atomique `IsActive → true` (garde WHERE `IsActive = false`) et audit `AdminUserReactivated` — **ne restaure jamais** les sessions révoquées ; l'utilisateur réactivé doit se reconnecter.
  - **Révocation de sessions autonome** (`POST /api/admin/users/{userId}/sessions/revoke`) : révoque toutes les sessions actives de la cible et audite `AdminUserSessionsRevoked` (métadonnée `revokedCount`) — idempotente par construction : un second appel révoque 0 session mais audite quand même l'opération.
  - **Réinitialisation 2FA admin** (`POST /api/admin/users/{userId}/two-factor/reset`) : désactive la 2FA (même jeu de champs que `User.DisableTwoFactor()` — secret actif/en attente et date de confirmation effacés), supprime tous les codes de récupération (`ITwoFactorRecoveryCodeRepository.DeleteAllForUserAsync`), audite `AdminUserTwoFactorReset`, puis envoie une notification Security obligatoire (`security.two-factor.admin-reset`) au titulaire du compte — **aucun secret** n'apparaît jamais dans l'audit ni dans la notification.
  - **Règles de ciblage** : l'auto-ciblage est rejeté (`ErrorType.Forbidden`) **avant tout appel repository**, pour les quatre actions. Un autre Admin peut être ciblé — aucune hiérarchie entre administrateurs n'existe dans ce codebase.
- **Journal d'audit** (`AuditLogEntry`, `Domain.Administration`) — append-only, cross-cutting (ne remplace aucun historique métier existant comme `RideStatusHistory`/`DocumentAccessAuditEntry`) :
  - **Sept types d'événement implémentés, ensemble fermé** : `AdminUserSuspended`, `AdminUserReactivated`, `AdminUserSessionsRevoked`, `AdminUserTwoFactorReset`, `RoleAssigned`, `RoleRemoved`, `AccountLocked`. Aucun `AccountUnlocked` (l'expiration du verrouillage est passive, sans opération explicite). Toutes les commandes ne sont pas auditées — seules ces sept.
  - **Métadonnées strictement en liste blanche**, jamais une capture générique par réflexion de l'entité : `revokedCount` (révocation de sessions), `role` (attribution/retrait de rôle), aucune métadonnée pour les cinq autres événements. Aucun mot de passe, hash, JWT, refresh token, valeur OTP, secret TOTP, code de récupération, clé de chiffrement, identifiant national, donnée bancaire ou GPS n'est jamais audité.
  - **Immuabilité à trois niveaux** : aucune méthode de mutation sur `AuditLogEntry` (propriétés en `private set`, uniquement une factory `Create`) ; mapping EF sans setter exposé ; déclencheur PostgreSQL (`trg_audit_logs_reject_mutation` / fonction `reject_audit_log_mutation()`) rejetant tout `UPDATE`/`DELETE` sur la table `AuditLogs` — prouvé par test d'intégration contre une vraie base. **Aucune garantie face à un superutilisateur de la base** n'est prétendue.
  - **`CorrelationId`/`IpAddress`/`UserAgent`** : colonnes nullables présentes, `IAuditContextAccessor` existe comme abstraction Application pure (`AuditLogEntry` ne dépend jamais de `HttpContext`). Depuis le Module 13B, `HttpCorrelationAuditContextAccessor` (API, seule classe du codebase reliant les deux) alimente réellement ces trois colonnes pour les sept événements audités, via `IHttpContextAccessor`/le middleware de corrélation — `NullAuditContextAccessor` (Infrastructure) reste le repli pour tout appelant non-HTTP (tests, traitement en arrière-plan), où les trois colonnes restent `NULL` comme avant.
  - **Cohérence transactionnelle** : pour les quatre actions admin ci-dessus, la mutation métier et l'insertion d'audit sont commises ensemble dans une seule transaction (`AdminUserManagementRepository`). Pour `RoleAssigned`/`RoleRemoved`, `AssignRoleCommandHandler`/`RemoveRoleCommandHandler` conservent exactement leur logique de validation existante et ne changent que leur appel de persistance final, désormais via le nouveau seam `IAuditedUserRepository.SaveWithAuditAsync` (mutation + audit dans une seule transaction). Seul `AccountLocked` reste best-effort/non transactionnel (déclenché par le système, sans acteur humain).
- **Verrouillage de compte** (extension additive de `User` — `FailedLoginAttempts`, `LockedUntilUtc`, `IsLockedOut(DateTime)`) :
  - **Compteur unifié** : un mot de passe erroné (`LoginUserCommandHandler`) et un code 2FA/récupération erroné (`TwoFactorChallengeCommandHandler`) incrémentent le **même** compteur via `IUserRepository.RecordFailedLoginAttemptAsync`, avec une garde conditionnelle atomique `ExecuteUpdateAsync` (même idiome que `PhoneVerificationOtpRepository`) — prouvé sans perte d'incrément sous accès concurrents réels.
  - **Configuration** (`LoginLockoutOptions`, section `LoginLockout`) : seuil par défaut **5** tentatives, durée de verrouillage par défaut **15 minutes**. Classe POCO liée via `IOptions`, sans validation de configuration dédiée ajoutée à ce jour ; aucun `SystemSetting` créé.
  - **Sécurité contre l'énumération** : compte inexistant, compte désactivé, compte verrouillé et mot de passe erroné renvoient exactement le même message générique (`"Email ou mot de passe incorrect."`, `ErrorType.Unauthorized`) — aucune de ces situations n'est distinguable côté client. Le compteur n'est jamais incrémenté pour un compte inexistant ou désactivé.
  - **Réinitialisation uniquement après authentification complète réussie** : une connexion directe réussie (sans 2FA) réinitialise le compteur ; un mot de passe correct suivi d'une 2FA en attente **ne** réinitialise **pas** encore le compteur ; seule la réussite du défi 2FA le réinitialise ensuite.
  - **Expiration passive** : `IsLockedOut(utcNow)` compare simplement `utcNow` à `LockedUntilUtc` — aucun job de déverrouillage, aucun événement `AccountUnlocked`.
  - `AccountLocked` est audité **une seule fois**, exactement au moment de la transition (nombre de tentatives atteignant le seuil), jamais à chaque tentative suivante pendant que le compte reste verrouillé.
- **Permissions** : exactement 3, Admin uniquement — `admin.users.manage` (suspend/reactivate/revoke-sessions), `admin.users.two-factor.reset` (isolée du fait de son risque élevé), `admin.audit-log.read` (lecture du journal, `GET /api/admin/users/{userId}/audit-log`). **Aucun nouveau rôle utilisateur** introduit.
- **Schéma ajouté** (migrations `AddAdministrationModule` + `AddAdministrationPermissions`) : table `AuditLogs` (avec ses deux index et le déclencheur append-only) ; `Users.FailedLoginAttempts` (entier, défaut `0`) ; `Users.LockedUntilUtc` (nullable, aucune valeur historique fabriquée — les comptes existants reçoivent `NULL`).

### 12B. Module 13B — Durcissement applicatif transverse (implémenté)

**BACKEND APPLICATION COMPLETE** — ce sous-module ferme la boucle applicative ouverte par 13A (collecte réelle de corrélation) et ajoute les protections transverses attendues d'une API de production : rate limiting, health checks, CORS, HSTS/en-têtes de sécurité, corrélation de requêtes, validation de configuration au démarrage. Il ne s'agit pas d'un module métier — aucune entité de domaine, aucune migration, zéro fichier modifié dans Rides/Fleet/Maintenance/RoadsideAssistance/Payment/Advertising/Support/Analytics/Subscription.

**DELIVERED — Module 13B**

- **Rate limiting** (`SmartTaxi.API.RateLimiting`) — six politiques nommées, chacune configurable via `RateLimiting` (`appsettings.json`), validée au démarrage (`RateLimitingOptionsValidator`, `ValidateOnStart()`) : `AuthCritical` (fenêtre fixe, 10/60s), `OtpAndChallenge` (fenêtre fixe, 5/300s), `PublicRead` (fenêtre fixe, 60/60s), `AuthenticatedGeneral` (fenêtre glissante, 120/60s, 6 segments), `AdminMutation` (fenêtre glissante, 30/60s, 6 segments), `SensitiveMutation` (seau à jetons, 10 jetons, réapprovisionnement de 1/6s). `RateLimitPolicySelector` résout la politique par route/méthode de façon centrale (un seul point de décision, jamais des centaines d'attributs `.RequireRateLimiting()` dispersés sur les endpoints). Clé de partition : IP distante pour un appelant non authentifié, `sub` du JWT (jamais le rôle) pour un appelant authentifié ; repli `"unknown-client"` si aucune IP n'est disponible. Le middleware de rate limiting s'exécute **après** `UseAuthentication()`, condition nécessaire pour que les politiques partitionnées par utilisateur voient un `HttpContext.User` peuplé. Réponse 429 en `application/problem+json` (jamais le type par défaut de `WriteAsJsonAsync`, qui écraserait silencieusement un `ContentType` déjà positionné), avec `correlationId`, et un en-tête `Retry-After` uniquement quand les métadonnées de bail de l'algorithme le fournissent réellement — jamais fabriqué. Aucune fuite de la clé de partition (IP/UserId) ni de configuration interne dans la réponse. `/hubs/rides` et `/hubs/notifications` sont explicitement exemptés (`.DisableRateLimiting()`), de même que les endpoints health.
- **Health checks** (`SmartTaxi.API.HealthChecks`) — `PostgresHealthCheck` (tag `ready`), exposé sur des endpoints dédiés distincts de liveness/readiness, jamais protégés par le rate limiting ni par l'authentification ; aucune fuite de détail interne (chaîne de connexion, message d'exception) dans la réponse en cas d'indisponibilité.
- **Corrélation de requêtes** (`SmartTaxi.API.Correlation`) — `CorrelationMiddleware`, unique point d'entrée : en-tête canonique `X-Correlation-ID`, validé par une expression régulière stricte (`[A-Za-z0-9-]{1,64}`), généré si absent ou invalide, toujours renvoyé dans la réponse, ajouté au scope du logger. Ne remplace jamais `HttpContext.TraceIdentifier` et n'est jamais confondu avec `Activity.TraceId` — deux identifiants distincts, à deux fins distinctes. `GlobalExceptionHandler` et le rejet 429 ajoutent `correlationId` directement dans leur `ProblemDetails` (ils court-circuitent `IProblemDetailsService`) ; les autres chemins d'erreur passent par `CustomizeProblemDetails`, dont la couverture réelle (y compris pour `TypedResults.Problem()`) a été vérifiée par test d'intégration, jamais supposée.
- **Contexte d'audit HTTP réel** (`HttpCorrelationAuditContextAccessor`, `SmartTaxi.API.Administration`) — implémente `IAuditContextAccessor` (Application) en lisant `IHttpContextAccessor`, et remplace `NullAuditContextAccessor` dans l'injection de dépendances pour toute requête HTTP réelle. Consommé effectivement (pas seulement enregistré) par les quatre actions admin (`AdminUserManagementRepository`), `AssignRoleCommandHandler`/`RemoveRoleCommandHandler`, et les deux chemins d'échec menant à `AccountLocked` (`LoginUserCommandHandler`, `TwoFactorChallengeCommandHandler`) — les sept types d'événement audités reçoivent désormais un `CorrelationId`/`IpAddress`/`UserAgent` réels lorsqu'ils proviennent d'une requête HTTP. Domain et Application restent entièrement dépourvus de toute dépendance à `HttpContext`.
- **En-têtes de sécurité et HSTS** (`SecurityHeadersMiddleware`) — `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cache-Control: no-store` sur toute réponse API (aucune ressource publique cacheable identifiée) ; les routes Scalar/OpenAPI (dev uniquement) sont explicitement exclues pour ne pas casser leur rendu. Aucune CSP ni Permissions-Policy ajoutée (délibérément hors périmètre de cette passe). HSTS (`max-age=30 jours`, `includeSubDomains=false`, `preload=false`) actif uniquement hors environnement `Development` ; vérifié manuellement (`curl` avec un en-tête `Host` non-localhost contre une instance `dotnet run --no-launch-profile`) car `HstsMiddleware` exclut intentionnellement `localhost`, quel que soit l'environnement — limitation de `TestServer`, pas du produit.
- **CORS** (`SmartTaxi.API.Cors`) — origines autorisées configurables (`Cors:AllowedOrigins`, vide par défaut), jamais `AllowAnyOrigin`. Validation stricte à la lecture de la configuration (URI absolue, schéma http/https uniquement, ni wildcard, ni chemin, ni query, ni fragment). Une liste vide désactive CORS pour toute origine cross-site (vérifié par test d'intégration, jamais supposé à partir de la seule sémantique de `WithOrigins()`).

- **Hors périmètre de Module 13B** (délibérément différé, non implémenté) : Content-Security-Policy, Permissions-Policy, configuration d'en-têtes `X-Forwarded-*` de confiance (nécessiterait de connaître la topologie réseau réelle de déploiement, non définie à ce jour), stockage distribué pour le rate limiting (multi-instance), `EnableRetryOnFailure()`/toute stratégie d'exécution EF Core (retravaillerait les 24 sites existants de transaction explicite, hors périmètre), Data Protection multi-instance.

**Périmètre différé, déjà approuvé, toujours hors de portée** (ni Module 13A ni 13B) :

- `SystemSetting` / paramètres système centralisés, feature flags, catalogue de zones géographiques, moteur de règles de rétention, rôles administratifs supplémentaires à moindre privilège (SuperAdmin, PlatformAdmin, SupportAgent, FinanceManager, AdvertiserAdmin, FleetManager, OperationsManager, ContentModerator, SecurityOfficer — le rôle `Admin` existant unique reste seul concerné par 13A).

**DEVSECOPS/DÉPLOIEMENT — jamais dans le périmètre applicatif de ce backend, entièrement non démarré** : OpenTelemetry, infrastructure de monitoring externe (Prometheus/Grafana), alerting, sauvegardes, gestion de secrets externalisée (type Secrets Manager), Docker, CI/CD, AWS (IAM/ECR/ECS/EKS), Kubernetes/Helm, Terraform/GitOps. Ce périmètre relève d'un parcours d'apprentissage distinct du développement backend et n'a jamais été traité par aucun des modules ci-dessus.

- **Données sensibles** : accès transverse à des données sensibles de plusieurs modules — contrôle d'accès strict par permission et journalisé pour les quatre actions admin ci-dessus ; côté Analytics implémenté, aucune donnée individuelle (email/téléphone/GPS/texte de ticket ou d'incident) n'apparaît jamais dans un agrégat.
- **Interactions réellement câblées (Analytics)** : lecture directe des tables Identity/Fleet/Rides/Payments/Subscriptions/Advertising/Maintenance/RoadsideAssistance/Support via `ApplicationDbContext`, jamais d'écriture, jamais de dépendance sur les repositories métier de ces modules.
- **Interactions réellement câblées (Administration — Module 13A)** : Identity uniquement — `IUserRepository`/`ISessionRepository`/`ITwoFactorRecoveryCodeRepository` (comptes, sessions, codes de récupération), Notifications (`INotificationDispatcher`, catégorie Security, notification obligatoire de réinitialisation 2FA). Aucune modification de Fleet, Rides, Payments, Subscriptions, Loyalty, Advertising, Maintenance, RoadsideAssistance, Support ou Analytics dans cette phase.
- **Interactions réellement câblées (Module 13B)** : composition root uniquement (`Program.cs`, `DependencyInjection.cs`) et Identity (les quatre gestionnaires listés en 12B, pour la consommation de `IAuditContextAccessor`). Zéro fichier modifié dans Ride/Fleet/Maintenance/RoadsideAssistance/Loyalty/Payment/Advertising/Support/Analytics/Subscription — vérifié par inspection exhaustive du diff avant documentation.
- **Règles d'isolation** : Analytics ne modifie jamais l'état d'un autre module. Administration (Module 13A) ne contourne jamais les règles métier d'Identity — `AssignRoleCommandHandler`/`RemoveRoleCommandHandler` conservent toute leur validation existante ; les actions de suspension/réactivation/révocation/réinitialisation réutilisent les comportements `User.Deactivate()`/`Activate()`/`DisableTwoFactor()` déjà existants plutôt que d'en réinventer la logique. Module 13B reste une couche transverse (middleware, options, composition root) : il ne détient aucune donnée métier et ne réimplémente la logique d'aucun module existant. Aucune infrastructure de monitoring externe n'est implémentée (Prometheus/Grafana/OpenTelemetry restent hors périmètre applicatif de ce backend).
